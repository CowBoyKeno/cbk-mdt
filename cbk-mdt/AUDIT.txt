I ran the deep exploit audit on the MDT package itself.

Verdict

This MDT is not trivially SQL-injectable, and the frontend does a decent job escaping HTML, but the resource still has a wide attack surface because it exposes a generic server RPC event and has very weak abuse controls.

Overall exploit rating

6.5/10 risk

That means:

not a “garbage public leak” level script

but absolutely not hardened enough for a serious production server

Attack surface

These are the real entry points an attacker or abusive player would target:

Network events

cbk_mdt:server:request — generic action router (server/server.lua:293)

cbk_mdt:server:appendActivity — direct officer activity write (server/server.lua:324)

cbk_mdt:server:radarHit — inserts radar log rows (server/radar.lua:65)

Client/NUI bridge

NUI callback mdt:request forwards arbitrary actions to server (client/client.lua:64-80)

NUI callback mdt:appendActivity forwards arbitrary log text to server (client/client.lua:82-90)

So the MDT is effectively a remote action bus with only a basic “is this person police?” check.

Critical findings
1) Generic RPC event can be spammed for database abuse

Severity: High

cbk_mdt:server:request accepts any registered action name and arbitrary payload, then dispatches it directly:

server/server.lua:293-322

Key issue:

there is no per-player rate limit

there is no cooldown by action

there is no payload size cap

there is no concurrency guard

That means a malicious police player can hammer:

get_dashboard

list_charges

get_officer_profile

search_citizens

search_reports

list_warrants

list_bolos

list_evidence

list_radar_logs

and force repeated DB reads.

Worse, some actions also write:

get_dashboard calls EnsureOfficer, which performs an upsert (server/server.lua:229-240, 37-56)

create/update actions write immediately

Why this matters

A single authorized player can generate:

DB saturation

server hitching

oxmysql queue buildup

log spam

frame degradation during peak population

Real abuse path

A player with police job can run a loop from a cheat menu or injected client:

spam TriggerServerEvent('cbk_mdt:server:request', ...)

use get_dashboard or search_*

create heavy DB churn without touching the UI

Fix

Add a server-side limiter:

global per-source request window

per-action cooldowns

drop oversized payloads

optionally audit/ban on flood

2) appendActivity is a direct DB write spam vector

Severity: High

cbk_mdt:server:appendActivity:

only checks CBK_MDT.IsOfficerAllowed(source)

then appends arbitrary strings to officer activity log

server/server.lua:324-331

AppendOfficerActivity():

loads current JSON log

decodes it

appends new entry

trims to 200

writes full JSON back

server/server.lua:60-86

Why this is bad

This is a classic write amplification pattern:

SELECT current log

decode JSON

append

encode JSON

UPDATE row

A malicious officer can hammer this event and generate constant read/write churn on mdt_officers.

Additional problem

The client sends raw activity strings:
client/client.lua:88

So the attacker controls:

action

details

Both are sanitized for control chars and length later, which is good, but that does not stop spam.

Fix

add cooldown, like 1 log event per 2–5 seconds

only allow specific whitelisted activity actions

remove direct client-driven activity logging entirely

generate activity server-side only after validated actions

3) No role separation inside police permissions

Severity: High

Every sensitive action uses the same gate:

CBK_MDT.RequireOfficer(source) → Framework.IsAllowed(source)

server/server.lua:146-153
shared/framework.lua:117-124

And Framework.IsAllowed() only checks whether the player’s job name is in:

Config.AllowedJobs
shared/config.lua:8-14

So if a player is any allowed police role, they can:

create or overwrite citizen records (server/citizens.lua:119)

edit citizen notes/flags (server/citizens.lua:84)

upsert vehicles (server/vehicles.lua:45)

flag vehicles stolen/clear (server/vehicles.lua:84)

create reports (server/reports.lua:23)

create warrants (server/warrants.lua:16)

update warrant status (server/warrants.lua:86)

create BOLOs (server/bolos.lua:16)

update BOLO status (server/bolos.lua:81)

add evidence (server/evidence.lua:15)

Why this matters

This is not a hacker-only problem. It is an insider abuse problem.

Any low-rank officer can alter mission-critical records.

Fix

Implement permission tiers:

view

report_writer

evidence_writer

warrant_writer

warrant_supervisor

bolo_writer

mdt_admin

Tie them to:

job grade

ACE perms

framework groups

High severity findings
4) No ownership or supervisory controls for records

Severity: High

There is no author or approval enforcement on updates.

Examples:

any allowed officer can update any warrant status (server/warrants.lua:86-115)

any allowed officer can update any citizen notes (server/citizens.lua:84-117)

any allowed officer can toggle any vehicle stolen flag (server/vehicles.lua:84-110)

any allowed officer can update any BOLO status (server/bolos.lua:81-110)

Impact

A random officer can:

clear another unit’s BOLO

serve/recall warrants they did not create

alter notes on high-risk citizens

remove or alter investigative vehicle flags

Fix

Add one or more of:

author ownership

supervisor override

immutable audit entries

approval workflow for warrant close/recall

5) Payload size is effectively unbounded

Severity: High

cbk_mdt:server:request deep-copies the payload before executing the handler:

server/server.lua:8-18
server/server.lua:311

There is:

no table depth cap

no element count cap

no total serialized size cap

Impact

An attacker can send very large nested tables to:

consume CPU during recursive deepCopy

consume memory

hitch the server before the handler even validates useful fields

Even though many handlers sanitize strings, the payload itself is copied first.

Fix

Before deepCopy(payload):

reject payloads above max key count

reject nested tables deeper than 4–5

reject oversized msgpack/json-equivalent input

optionally whitelist expected payload schema per action

6) Report creation can be abused for oversized JSON rows

Severity: Medium-High

create_report clamps array lengths:

server/reports.lua:49-63

That is good.

But it does not sanitize the contents of each table entry inside:

involved_citizens

involved_vehicles

evidence_refs

Those entire tables are JSON-encoded directly:

server/reports.lua:79-84

Impact

An attacker can send:

bloated objects

useless nested junk

garbage keys

oversized embedded strings

Even with a limited number of list items, each item can still be large.

Fix

Normalize each list entry into a strict schema:

citizen: { identifier, name }

vehicle: { plate, model }

evidence ref: { id }

Do not encode arbitrary client tables.

7) Evidence metadata is arbitrary table input

Severity: Medium-High

add_evidence accepts payload.metadata if it is a table and stores it as JSON:

server/evidence.lua:27-55

There is:

no schema validation

no depth cap

no size cap

no key whitelist

Impact

This can be abused as a storage bloat vector.

Fix

Whitelist metadata keys by evidence type, for example:

photo: { camera, timestamp }

casing: { caliber, serial }

fingerprint: { match_score }

Medium severity findings
8) Radar event is rate-limited, but not safely enough for production

Severity: Medium

This is one of the better parts of the script.

cbk_mdt:server:radarHit has a per-source 350 ms limiter:
server/radar.lua:16-25

That is good.

But:

it still writes one DB row every 350 ms

there is no batch queue

no max speed sanity check

no verification that radar data came from an actual equipped unit/state

no duty-state validation

Impact

An allowed officer can still generate a lot of rows.

Fix

batch insert radar logs

add speed range sanity

verify player is in police vehicle / on duty

server-side source integration only

9) Missing audit immutability

Severity: Medium

The script appends officer activity, but the system is not truly forensic:

actions are not hash chained

records are mutable elsewhere

no immutable “who changed what” tables exist

If a corrupt officer changes citizen notes, clears a vehicle, and closes a BOLO, you do not have a strong audit trail.

Fix

Create append-only audit tables:

mdt_audit_citizens

mdt_audit_vehicles

mdt_audit_warrants

mdt_audit_bolos

Store:

actor identifier

old value snapshot

new value snapshot

action type

timestamp

10) No source/session freshness checks

Severity: Medium

The server trusts source being valid at call time, which is normal, but it does not verify:

on-duty state

current department

job freshness after async delay

whether the player is still connected before sending response

This is not the biggest issue here, but on larger servers it becomes relevant.

Lower severity / good news
11) SQL injection risk is low

Severity: Low

Good:

database queries use parameter binding

I did not find raw string concatenation of user data into SQL statements

That removes the most obvious SQLi class.

12) Frontend XSS is mostly handled correctly

Severity: Low

escapeHtml() is used in rendered templates:
web/app.js:60-68

That is a good sign.

I did not see an obvious stored XSS path in the current UI rendering.

Still, keep in mind:

XSS safety depends on always using escapeHtml

future UI additions can easily break this

Practical exploit scenarios
Scenario A — police insider DB flood

A low-rank officer binds a loop to:

cbk_mdt:server:request with get_dashboard

cbk_mdt:server:appendActivity

Result:

repeated officer upserts

repeated JSON activity rewrites

repeated dashboard queries

oxmysql churn and server hitching

Scenario B — unauthorized record tampering inside PD

A regular officer:

closes BOLOs they did not create

recalls or serves warrants they should not control

edits citizen notes for protected profiles

clears stolen flags on vehicles

Result:

operational integrity failure, even without an external hacker

Scenario C — payload bloat hitch

An attacker with police access sends a huge nested table to cbk_mdt:server:request.

Result:

recursive deepCopy overhead

memory churn

possible hitching before normal handler validation

Priority fix order
Priority 1

Lock down the generic RPC bus.

add per-source rate limits

add per-action cooldowns

cap payload size/depth

log and punish abuse

Priority 2

Remove client-driven activity logging.

no direct appendActivity event from client

server generates logs only after successful validated actions

Priority 3

Add real permissions.

viewer

officer

supervisor

command

mdt_admin

Priority 4

Enforce record ownership / approval.

only creator or supervisor can close/recall

only approved roles can update citizen flags

audit every mutation immutably

Priority 5

Normalize schemas.

strict payload validation for report lists and evidence metadata

Final assessment

This MDT is architecturally cleaner than most FiveM MDT releases, but from an exploit-hardening perspective it still has the classic weakness of many RP police tools:

it trusts “police job = full trusted operator.”

That is the biggest design flaw.

It is not currently a “remote arbitrary server compromise” script, but it is absolutely vulnerable to insider abuse and DB-flood abuse.
